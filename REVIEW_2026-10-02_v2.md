## 🔴 Critical

### C1 — Founder-email admin bypass is STILL LIVE in the live-database function `admin_delete_user`
- **Files:** `supabase/schema.sql:296-301` (generated from the live catalog — i.e., this is what's actually in production), `supabase/migrations/20260830_add_admin_delete_user_rpc.sql:12`
  ```sql
  IF NOT EXISTS (SELECT 1 FROM public.users WHERE id = auth.uid() AND role = 'admin')
     AND COALESCE(auth.jwt() ->> 'email', '') <> 'saddamakash234@gmail.com'
  THEN RAISE EXCEPTION 'Admins only'; END IF;
  ```
- **What's wrong:** The 2026-09-30 audit's H2 (founder-email bypass) was removed from *app code* (`lib/auth.ts` documents "Roles are the SOLE authority… no email-based founder bypass"), but the **live DB function retains it**. The function is `SECURITY DEFINER` with `EXECUTE` granted to `authenticated`, and it's directly callable by any signed-in user via PostgREST (`POST /rest/v1/rpc/admin_delete_user`) — the `requireAuth('admin')` gate in `app/api/admin/delete-user/route.ts` does not protect the RPC itself. Any session whose JWT email is `saddamakash234@gmail.com` can delete **any user account** (all admins included; only self-deletion is blocked) without `users.role = 'admin'`.
- **Why it matters:** A backdoor that **survives role demotion** — if the founder's `users` row is ever deleted/demoted (or during any future admin dispute), the email check still grants delete-any-user power. Also a hardcoded personal email in the live schema.
- **Exploit prerequisite (nuance):** requires a valid Supabase session for the founder's email, so this is not remotely exploitable by strangers today — but it is a live privilege-escalation primitive contradicting a documented security invariant.
- **Fix:** New migration on the Main project: replace the guard with `IF get_my_role() <> 'admin' THEN RAISE EXCEPTION 'Admins only'; END IF;` (per AGENTS.md, `get_my_role()` is the role source — never `auth.role()`), delete the email clause entirely, regenerate `supabase/schema.sql`. Consider revoking `authenticated` EXECUTE so only the admin-gated API route can reach it.

## 🟠 High

### H1 — Owner-rights views expose foundation financials + every member's pledge to ANY signed-in user
- **Files:** `supabase/schema.sql:617-619` (comment: *"no security_invoker is set, so views run with owner rights (RLS on the base tables does NOT apply)"*), grants at `:806`, `:827`, `:834`, `:848`, `:862`, `:876` — `GRANT SELECT ON public.{donation_summary, expense_summary, expense_category_summary, monthly_collection_summary, member_summary, member_directory} TO authenticated, service_role`
- **What's wrong:** RLS on `donations`/`members` carefully restricts members to their own rows, but these six views bypass RLS by design and are readable by **every logged-in user, including unapproved members** (they hold a session):
  - `donation_summary` → foundation-wide total donations; `expense_summary` / `expense_category_summary` → totals by category; `monthly_collection_summary` → per-month target/collected/net_balance;
  - `member_directory` (`:633-640`) → every member's `id, name, join_date, status, monthly_pledge, created_at` — pledge amounts are sensitive.
- **Reached from the client:** `app/dashboard/page.tsx:59-63` fetches all four financial summaries **unconditionally for every role**; `app/members/page.tsx:48-50` fetches `member_directory` (`select("*")`, incl. `monthly_pledge`) for non-staff. The members page hides phone/address in the UI, but `monthly_pledge` ships over the wire to every member's browser.
- **Fix (pick one):** `ALTER VIEW … SET (security_invoker = true)` on all six views so base-table RLS applies, **or** revoke `SELECT … TO authenticated` and expose aggregates through staff-gated RPCs. Also gate the dashboard summary fetches on the staff view.

## 🟡 Medium

### M1 — `calculate_payment_allocation` is a pledge-amount oracle for any authenticated user
- **File:** `supabase/schema.sql:358-364` — `SECURITY DEFINER`, `authenticated=EXECUTE`. All inputs (`p_member_id`, `p_payment_amount`, `p_pledge_history`) are caller-supplied; internally it reads `members.monthly_pledge` for the given member, bypassing RLS.
- **What's wrong:** Any signed-in member can call `rpc('calculate_payment_allocation', {p_member_id: <victim>, …})` and read back per-month allocations equal to the victim's monthly pledge. Independent of H1 and survives an H1 fix.
- **Fix:** Revoke `authenticated` EXECUTE (service_role only — the app never calls it from the client), or add an internal staff/owner check.

### M2 — `log_audit_event` misattributes service-role writes to a random admin
- **File:** `supabase/schema.sql:461-472`: `v_actor_id := coalesce(auth.uid(), (SELECT id FROM public.users WHERE role = 'admin' LIMIT 1))`
- **What's wrong:** Every service_role write (payments, sheets restore, backfills — the writes that matter most) has `auth.uid()` NULL, so the audit row is pinned on an **arbitrary admin** (`LIMIT 1`, no `ORDER BY`). Forensic integrity of `audit_log` is broken for exactly the most sensitive writes.
- **Fix:** Allow `actor_id` NULL for system writes and set `actor_email = 'system@foundation.app'` (already the email fallback); never attribute to a human who didn't act.

### M3 — `POST /api/admin/reset-password`: no audit trail, can target fellow admins
- **File:** `app/api/admin/reset-password/route.ts:1-50`
- **What's wrong:** Uses `adminClient.auth.admin.updateUserById` (touches `auth.users` only → no trigger fires → **zero audit record** of who reset whose password). No check that `userId` isn't another admin; `MIN_PASSWORD_LENGTH = 8` with no complexity requirement.
- **Fix:** Insert an `audit_log` row (service client) on every reset; forbid resetting other admins' passwords (or require step-up re-auth).

### M4 — `restore-sheets` / `sync-sheets` POST leak "Sheets configured?" to unauthenticated callers
- **Files:** `app/api/restore-sheets/route.ts:14-17`, `app/api/sync-sheets/route.ts:14-17`
- **What's wrong:** Both POST handlers call `getSheetsConfig()` **before** `requireAuth('admin')`, returning `200 {enabled:false}` without auth vs `401` when configured — a config oracle. The GET handler in the same file (`:31-36`) is explicitly gated with the comment *"an unauthenticated caller must not learn whether Google Sheets backup is configured"* — the POST handlers leak the same bit.
- **Fix:** Move `requireAuth('admin')` above the config check in both POST handlers.

### M5 — `restoreFromSheets` writes to a removed column; errors swallowed; N+1
- **File:** `lib/sheets-sync.ts:225-300`
- **What's wrong:** Line 256: `row.user_id = (r as any)[7] || fallbackUserId` — but `members` has **no `user_id` column** (`supabase/schema.sql:91-103`; the auto-link route comment confirms removal). Every member insert therefore fails; the error is never checked, yet `result.members.updated++/added++` counts it as success. Also: per-row SELECT→UPDATE/INSERT (N+1 over service role), `Number(pledge ?? 0)` can store NaN, no date/amount validation on sheet data.
- **Fix:** Drop the `user_id` assignment, check every write error and surface failures, validate/normalize rows, batch writes. (The `as any` cast at `:256` is exactly what hid this — see L7.)

### M6 — Brand-name Unicode inconsistency on the public verify page
- **Files:** `app/verify/[receipt_no]/page.tsx:17` (metadata description), `:81` (BrandHeader)
- **What's wrong (byte-verified):** these two lines spell `দৌলখাঁড়` with **decomposed** ড (U+09A1) + ় nukta (U+09BC); the other 16 occurrences app-wide (receipt masthead `ReceiptPaper.tsx:72`, layout metadata, manifest) use **precomposed** ড় (U+09DC). They render nearly identically but are different strings — metadata/SEO mismatch and brand inconsistency on a public page, and any cross-page string search/comparison silently fails.
- **Fix:** Replace both with the canonical precomposed form used everywhere else.

### M7 — 10 headings miss `font-shadhinata`, silently fall back to Tiro (incomplete rollout)
- **Files:** `app/admin/page.tsx:171`, `app/dashboard/page.tsx:175`, `app/donations/page.tsx:131,136,138`, `app/joma/page.tsx:793,1000,1076,1153`, `app/reports/page.tsx:275`
- **What's wrong:** 64 of 74 `h1`/`h2`/`h3` elements carry `font-shadhinata`, but these 10 don't — they render in Tiro Bangla via the `h1,h2,h3 { font-family: var(--font-tiro) }` base rule in `app/globals.css:37-40`, contradicting the declared role contract ("Shadhinata 2.0 = headings"). Page titles vs section headings are visibly different typefaces on 5 pages.
- **Fix:** Add `font-shadhinata` to the 10, or change the base rule to `var(--font-shadhinata)` so the default is correct.

### M8 — Synthetic bold on all Lipighor fonts
- **Files:** pervasive — every `font-shadhinata` heading, `ReceiptPaper.tsx` detail values, masthead
- **What's wrong:** Only Regular (400) TTFs are bundled for shadhinata/nakkhatra/teesta/akkas, yet `font-bold`/`font-semibold` is paired with them everywhere. Browsers synthesize the bold; on Bengali this can look muddy/heavy vs a true cut (the masthead bold was a deliberate choice, but the pervasiveness wasn't).
- **Fix:** Accept as intentional, or ship real bold TTFs if Lipighor provides them.

### M9 — Typography commits `77a1919`/`82bbb52` not documented in CHANGELOG/COMMIT_LOG
- **Files:** `CHANGELOG.md`, `COMMIT_LOG.md` (no entries for the two commits)
- **What's wrong:** Per `AGENTS.md` doc-sync rules, user-facing changes belong in `CHANGELOG.md [Unreleased]` and behavior changes in `COMMIT_LOG.md`. The parent session planned this step but it was skipped when the push pivoted to the connector.
- **Fix:** Add entries (docs-only commit).

## 🟢 Low

### L1 — PostgREST filter injection in `pending-pledges` (`month` param)
- **File:** `app/api/admin/pending-pledges/route.ts:32-39`: `` .or(`donation_month.lte.${month},donation_month.is.null`) `` with `month = searchParams.get("month")` — no format check. Admin-only route, so impact is limited to a widened/nonsensical filter — but validate with `/^\d{4}-(0[1-9]|1[0-2])$/` before interpolating.

### L2 — `Content-Disposition` header injection via `receipt_no`
- **File:** `app/api/receipts/[id]/route.ts:445`: `` filename="receipt_${donation.receipt_no || id}.jpg" ``
- **What's wrong:** `POST /api/payments` blocks only `\r\n\t` and length > 64 in `receipt_no` — **`"` is allowed**; bulk import (`COLUMN_RULES.donations.receipt_no: "string"`) allows anything including quotes/CRLF. A crafted receipt_no can break out of the quoted filename.
- **Fix:** Sanitize (`receipt_no.replace(/["\r\n]/g, "")`) or use `filename*=UTF-8''` encoding.

### L3 — `/api/receipts/[id]` fetches the donation before authorization → 403/404 oracle
- **File:** `app/api/receipts/[id]/route.ts` — donation fetched (404) before `canView` check (403). UUIDs are unguessable, so negligible — noted for completeness. The `isStaff || own-member` check itself is correct.

### L4 — `/api/qr` rate limit is real but weak
- **File:** `app/api/qr/route.ts:39-45`
- **What's wrong:** In-memory `Map` is per-instance (no shared state on serverless/multi-instance), and the key is the trivially spoofable `X-Forwarded-For`. A determined attacker rotates the header × instance count; QR rendering is CPU-bound. (512-char cap, try/catch→422, and the limiter itself verified present and correct.)
- **Fix:** Rate-limit at the edge keyed on verified client IP; keep the in-app limiter as a second layer.

### L5 — Public `/verify/[receipt_no]` + sequential receipt numbers = enumerable ledger
- **Files:** `generate_receipt_no()` (`supabase/schema.sql:396` → `R-0001, R-0002…`), `app/verify/[receipt_no]/page.tsx` (public; returns amount, months, date, collector per receipt; donor name masked — good)
- **What's wrong:** Anyone can walk the sequence and reconstruct donation amounts/timing. Accepted trade-off for QR verification, but consider non-sequential receipt numbers (e.g. `R-<random>`).

### L6 — Unnecessary `EXECUTE` grants
- **File:** `supabase/schema.sql:396` — `generate_receipt_no` granted to `anon` (harmless — RLS applies — but pointless surface); same for `get_my_*` helper `anon` grants. Tidy up.
